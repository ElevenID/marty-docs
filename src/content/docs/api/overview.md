Use your deployment's **HTTPS origin**, such as `https://gateway.example.org`.
Public versioned API paths start with `/v1`; do not add a website-specific `/api`
prefix. Health and discovery routes have their own paths.

## Discover the installed contract

| Path | Purpose |
| --- | --- |
| `GET /openapi.json` | OpenAPI document generated by the installed gateway |
| `GET /docs` | Interactive API documentation |
| `GET /health` | Gateway health |
| `GET /health/ready` | Readiness, including dependencies |
| `GET /.well-known/marty-release` | Installed release identity |
| `GET /v1/protocol-support` | Protocol support catalog |

Record the release identity with integration evidence. Examples here are grounded
in [gateway source at b7c70558](https://github.com/ElevenID/marty-ui/tree/b7c7055830722d10512ccac042b1e0abe0e1ecec/rust/services/gateway/src);
compare them with your installed `/openapi.json` before selecting newer features.

## Authentication and scope

Use an organization API key in `X-API-Key`. Ordinary OAuth bearer tokens are not
accepted as gateway machine credentials. The
[authentication guide](/getting-started/authentication/) explains bootstrap,
explicit scopes, private storage, and rotation. Organization identifiers select
resources; they cannot expand the key's organization boundary.

## Main integration operations

| Operation | Route | Result |
| --- | --- | --- |
| Read templates | `GET /v1/credential-templates?organization_id=…` | Template inventory |
| Read a template | `GET /v1/credential-templates/{id}` | Template configuration |
| Initiate credential issuance | `POST /v1/issuance` | Transaction and credential offer |
| Read an issuance transaction | `GET /v1/issuance/{id}` | Transaction state |
| Read an issued record | `GET /v1/issued-credentials/{id}` | Persisted credential metadata |
| Verify with a saved policy | `POST /v1/vc-api/credentials/verify?organization_id=…&presentation_policy_id=…` | Synchronous policy-backed verdict |
| Read trust profiles | `GET /v1/trust-profiles?organization_id=…` | Trust profile inventory |

Issuance offers are redeemed through the endpoints in issuer and authorization
server metadata. Do not assume that the initiation response contains the signed
credential or hard-code a token endpoint from another deployment.

## Errors and retries

Read the HTTP status, response body, and `X-Correlation-ID` when supplied. The
gateway and domain services may use different error shapes; do not require a
single invented error envelope.

| Status | Typical action |
| --- | --- |
| `401` | Check the credential type, key validity, and header |
| `403` | Check organization ownership and all operation scopes |
| `409` | Reconcile an in-progress operation, conflicting state, or reused idempotency key |
| `422` | Correct the request or inspect the rejected verification result |
| `502` / `503` | Check dependencies and preserve any uncertain mutation state |

Use a stable `Idempotency-Key` for a logical issuance event. Do not assume a
timeout means no transaction was created. Gateway replay caching and downstream
durable deduplication are separate behaviors: qualify both for the installed
release before enabling automatic mutation retries. The course example journals
every mutation and does not retry it automatically.
